## 2. Findings

### F1 — P1 — Any dhikr over ~850 folded characters cannot be saved (HTTP 500)

`Dhikr.SearchText` is indexed (`ContentConfig.cs:61`) and SQL Server caps a nonclustered
index key at 1700 bytes. `ContentRules.MaxIndexedSearchLength = 850` exists for exactly this
and its own doc-comment describes the failure — but the admin path never applies it:

- `ContentAdminService.cs:304` (create) — `SearchText = ArabicText.Normalize(arabic)`
- `ContentAdminService.cs:355` (update) — same, recomputed on *every* save

The Qur'an paths (`QuranicAthkarSeeder.cs:110`, `QuranAthkarSyncService.cs:142`) do apply it.

**Threshold proven through the API** (`POST /api/v1/admin/content/adhkar`):

| folded Arabic | bytes | result |
|---|---|---|
| 839 ch | 1678 | 200 OK |
| 845 ch | 1690 | 200 OK |
| **851 ch** | **1702** | **HTTP 500** |
| 2399 ch | 4798 | HTTP 500 |

Secondary breach: this returns **HTTP 500**, violating the project's "errors are HTTP 200 +
failed envelope" rule. `DhikrInput.ArabicText` permits `MaxTextLength = 4000`, so the contract
promises four times what the database accepts. Because `Normalize` strips diacritics, a heavily
vocalised 1700-character dhikr folds *under* the limit while a plain 851-character one does not —
the failure point is invisible to the editor.

**Not covered by any of the 193 backend tests.**

### F2 — P1 — The 14 Qur'anic adhkar cannot be edited in the CMS at all

`ContentAdminService.cs:583` returns a dhikr's translation as `TranslationInput.Title`:

```csharp
Title = t.Translation,     // DhikrTranslation.Translation — up to 4000 chars
```

but on the way back in, `TranslationInput.Title` is `[Required, StringLength(500)]`.
The seeded Qur'anic translations are 3342 (ar) and 3998 (en) characters, so the edit form
**cannot round-trip its own data**.

Reproduced through the real UI: opened «السجدة: ١-٣٠» in the control panel, changed nothing,
pressed حفظ →

```
PUT /api/v1/admin/content/adhkar/52 → 200
{"success":false,"errorCode":2,
 "message":"The field Title must be a string with a maximum length of 500.",
 "errors":[ ...same, twice — once per language ]}
```

On screen the editor sees only **«راجع الحقول المميّزة»** — no indication of which field, no
mention of a length, and no achievable fix (the text is Qur'an; it cannot be shortened).
`unpublish`/`publish` still work, because they do not touch translations.

### F3 — P2 — The CMS unit suite is red and nothing in the workflow catches it

`widget-catalog.component.ts:108` calls `this.api.widgetSettings()`; the spec's `ApiService`

A stale stub, not a product bug — but `CLAUDE.md`'s pre-merge checklist lists `npm run build`

`translations-editor.component.spec.ts` (4 tests) passes.

### F4 — P3 — Arabic folding diverges between server and app on astral characters

`CLAUDE.md` requires `ArabicText.cs` and `arabic_text.dart` to be exact mirrors. Every
fold rule matches. One structural difference does not:

- **C#** iterates `foreach (var ch in raw.Normalize(FormC))` — UTF-16 **chars**. An emoji
  arrives as two lone surrogates; `char.IsSymbol` is false for each, so both are **kept**.
- **Dart** iterates `raw.runes` — **code points**. The emoji matches `\p{S}` and folds to a space.

Verified on both sides with the same input `"الحمد 😀 لله"`:

| | result |
|---|---|
| Dart | `الحمد لله` (emoji dropped) |
| C# (stored `SearchText`) | `الحمد ‹2 chars› لله` (emoji kept) |

`U+1EE00` (Arabic Mathematical) is category `Lo` and survives on both sides, so the divergence
is confined to symbol/emoji astral characters. Low real-world impact; the two test corpora hold
**26 identical Arabic literals with zero divergence**, but neither covers astral input.

### F5 — P3 — `AppException` with no message leaks the .NET type name to clients

`GET /api/v1/devices/notifications` without `X-Device-Key`:

```json
{"success":false,"errorCode":201,
 "message":"Exception of type 'Athkar.Shareds.Models.AppException' was thrown."}
```

`RequireDeviceKey()` throws `new AppException(ErrorCode.InvalidDeviceKey)` with no message, so
the framework default surfaces. The `errorCode` is correct and clients map from it, so this is
cosmetic — but it ships an internal namespace to every caller.

### F6 — Observation — seeder failed once at first API start, same root cause as F1

The session's first `dotnet run` logged:

```
SqlException 1946: Operation failed. The index entry of length 2120 bytes for the index
'IX_Adhkar_SearchText' exceeds the maximum length of 1700 bytes for nonclustered indexes.
   at QuranicAthkarSeeder.SeedAsync ... line 112
```

2120 bytes = 1060 chars = exactly the folded length of the `imran-tafakkur` block
(`3:190-200`) in `athkar_quranic.json`. The current build trims correctly (max stored
`SearchText` is 848) and a restart is clean, because the seeder's
`if (await db.Adhkar.AnyAsync(...)) return;` guard short-circuits once the chapter is filled.
Not reproducible on the current binary — recorded because it is the same root cause as F1 and
because the guard means a *partial* seed would never self-heal.

## 3. Rules verified as holding

| Rule | Evidence |
|---|---|
| `ContentVersion` is the sync protocol | bumped on create (48→49) and on delete (50→51) |
| Publish requires a source | published-without-source refused (`errorCode 304`); draft allowed; publishing that draft refused |
| Prayer-anchored ⇒ `DeviceLocal` (§5) | created with `delivery: ServerPush` → returned `DeviceLocal`; update cannot re-force it; campaign reaches public `/reminders` |
| Inbox is the delivery, push a courtesy | with no FCM credentials, broadcast still wrote the device inbox row; read / read-all work |
| Soft delete hides everywhere | gone from admin GET (`errorCode 301`) and from the public catalog |
| Logout revokes immediately | `auth/me` on the same token → 401 (`ClockSkew = 0`) |
| Role ladder | Editor **can** read content; **cannot** list staff, read audit, change configuration, or create a SuperAdmin — all 403 `errorCode 5` |
| Anonymous-device brake | 5 open feedback accepted, 6th refused (`errorCode 702`) |
| Push token is a lease | rotation accepted; unknown device key refused rather than upserted |
| No coordinates server-side | `lat`/`lng` in a register body are neither echoed nor stored; admin device rows expose none |
| Arabic folding equivalence | istighfar and «الله» fold identically across hamza / diacritics / tatweel / alif-maqsura spellings |
| Folding corpus parity | 26 Arabic literals, C# ∩ Dart = 26, symmetric difference = 0 |
| Umm al-Qura follows the country | Dammam: Maghrib ٥:٤٦ + 90 min = Isha ٧:١٦ exactly |
| Qibla correctness | Dammam → 244° SW, ١١٨٠ km (independently computed: 244.2°, ~1180 km) |
| Traceability visible to the reader | every dhikr card carries book + number + grade («صحيح مسلم ٢٧٢٣ / صحيح») |
| Envelope discipline | validation and domain failures return HTTP 200 + failed envelope — except F1 |

## 5. Environment notes

- `Stop-Process` on the `dotnet run` PID leaves the child `Athkar.exe` holding port 5000; the
  relaunch then dies with `AddressInUse` while the *old* process keeps serving. Kill `Athkar.exe`
  by name, or the restart silently tests the previous build.
- `ng test --browsers=ChromeHeadless` fails on this repo — it is vitest, and the flag wants
  `@vitest/browser-*`. Plain `npx ng test --watch=false` works.

## 6. Suspicions that turned out to be my own error

1. `?q=` on `content/search` — the parameter is `search` (`PageInput`); `q` yields an empty term and 0 hits, correctly.
2. `translations[].title` omitted — it is `[Required]`.
3. `delivery: 0` / `anchorType` — `ReminderDelivery` is 1-based and the fields are `kind` + `anchor`.
4. `roles: <int>` on staff create — it is `roles: [<int>]`, a list.
5. Broadcast `status == 1` read as "still Draft" — `1` is `Scheduled`; `Draft` is `0`, so it *had* advanced.
6. «العافية» returning 0 hits read as a ta-marbuta folding failure — the word simply was not in the corpus; folding is correct.
